# SMITE CMS v2.0.0 — Release Notes

**Release version:** `v2.0.0`  
**Release type:** Major application release (first V2 CORE)  
**Date:** 2026-08-31  
**ADR:** [ADR-027 — V2 Scope and Backward Compatibility](../adr/ADR-027-V2-Scope-and-Backward-Compatibility.md)

## Summary

SMITE CMS **v2.0.0** is the first V2 application release. It delivers the three P0 CORE features defined in ADR-027 on top of the frozen V1 distribution baseline (`v1.1.6`). Public site behavior, Theme 2026, and existing admin content workflows remain backward compatible.

**Latest repository distribution:** `v2.0.0`  
**V1 historical baseline:** `v1.1.6` (frozen; no further V1 releases)

## V2 CORE scope (this release only)

| ID | Feature |
| --- | --- |
| P0-1 | User Management UI |
| P0-2 | Password Reset Email Delivery |
| P0-3 | Password Policy Consistency |

P1/P2 items (audit filters, tag lifecycle, menu drag/drop, analytics, etc.) are **not** included.

---

## P0-1 — User Management

Admin users with the `user.manage` permission can manage staff accounts at `/admin/users`:

- List users (username, role, active status; email masked in list)
- Create **Editor** or **Contributor** accounts
- Edit staff (email, role, active status)
- Activate and deactivate staff
- Change roles between Editor and Contributor

**Single-Admin protection:**

- The **Admin** role **cannot** be created or assigned through the V2 user-management UI
- The sole Admin cannot be deactivated or demoted if that would leave zero usable Admins

**Security & PII:**

- Email stored encrypted at rest with HMAC lookup hash (ADR-008)
- Passwords never appear in list UI, audit metadata, or responses
- Audit events: `USER_CREATED`, `USER_ACTIVATED`, `USER_DEACTIVATED`, `USER_ROLE_CHANGED`

Editors and Contributors without `user.manage` cannot access user management routes.

---

## P0-2 — Password Reset Email

When SMTP is configured, password reset requests at `/cp/password-reset` deliver a reset link by email.

**Preserved token mechanism:**

- 32-byte random token (`random_bytes(32)`)
- 1-hour TTL (3600 seconds)
- Single-use (cache key consumed on successful reset)
- Token stored in cache only — not in the database
- Opaque responses (no email enumeration)
- Throttling and CSRF remain active

Reset URL is built from configured `app.baseURL` — not hard-coded.

SMTP failures are logged generically; the user still sees an opaque success message on request.

---

## P0-3 — Password Policy Consistency

All password-setting surfaces now delegate to the authoritative **CodeIgniter Shield** password policy (`service('passwords')->check()` via `PasswordPolicyService`):

1. Initial Admin installation (`cms:install`)
2. Forced first-login password change (`/cp/password-change`)
3. Password reset verification (`/cp/password-reset/verify`)
4. Admin recovery (`/cp/admin-recovery`)
5. Staff user creation (`/admin/users`)

Password rules are defined in `app/Config/Auth.php` (minimum length, composition, personal-information, dictionary validators). No duplicate application-level password rules were added.

---

## Backward compatibility

- Public routes unchanged: `/`, `/{slug}`, `/news/{slug}`, `/en/...`
- `/news` without a post slug remains reserved (404 for Pages)
- Auth surfaces unchanged: `/cp`, password change, reset, recovery
- Theme 2026, media upload paths, audit architecture, and existing admin modules preserved
- No new roles, API, SPA, queue, or Redis requirement

## Database / migration

**No database migration is required for v2.0.0.**

V2 CORE uses the existing Shield and application schema from V1.

## Upgrade from V1.1.6

See [UPDATE.md](../client/UPDATE.md). Summary:

1. Back up database and uploads (`public/uploads/images/`, `writable/uploads/documents/`)
2. Preserve `.env`
3. `git fetch --tags && git checkout v2.0.0`
4. `composer install --no-dev --prefer-dist --optimize-autoloader`
5. Run `php spark migrate` **only if** future releases add migrations (not required for v2.0.0)
6. Clear cache if applicable; smoke-test `/` and `/cp`

**Do not** run `cms:install` or `cms:demo` on an existing production installation.

## Security highlights

- CSRF, throttling, and opaque auth failures preserved (ADR-026)
- PII encryption and HMAC lookup unchanged (ADR-008)
- Reset tokens and passwords excluded from logs and audit metadata
- User management authorization enforced server-side

## Known non-blocking technical debt

- `auth_identities.secret` may be empty after install (intentional PII protection; login uses username)
- Shield `NothingPersonalValidator` rejects passwords containing username or email fragments (including at install)
- Encrypted email is not loaded onto the Shield `User` entity at runtime for personal-password checks on persisted accounts

These items were assessed in V2-006 and are not release blockers.
